# 驱动带起与故障定位

## 时钟、复位、IOC

不少 Rockchip 寄存器使用高16位写使能、低16位值，但必须逐寄存器核实。
状态位、W1C、普通读写位不能混用同一写法；sticky reset cause 是结果，
不是路由使能。

将时钟注册成命名 mux/divider/gate 链。驱动申请/开启依赖，设置目标频率，
读取实际频率用于控制器分频，并回收半途失败资源。记录与 loader 旧状态
的差异；“以往 loader 已打开”不等于驱动自己完成了初始化。

K7 eMMC 的 SDHCI 分频字段曾未改变实际输入时钟，直到设置 CRU 才达到
目标频率。时钟API回报值、软件推导值、引脚/实际吞吐是不同证据；不要用
其中一项冒充其他项。参考案例 [团队PR54](https://github.com/open-vela/contest2026_062_PharosTech/pull/54)。

GPIO API 使用当前源码提供的 handle/setter；pinset 只承担其契约规定
的身份字段。板级函数明确配置复用、上下拉、驱动强度和方向。
PMU IOC 与主 IOC 的电源、安全和寻址规则需分别证明，避免裸写挂总线。

## 存储验证顺序

1. 控制器 reset 与 update-clock 完成。
2. 测量或读回低速识别时钟，核对命令和原始状态位。
3. CMD0 及该协议的工作条件协商。
4. 单块 PIO 读取，核对固定内容。
5. 在指定测试区域写入并读回；测试范围须明确，不能任意覆盖介质。
6. 多块、中断、DMA、文件系统与恢复分别验证。

DW-MSHC 与 DW-CM-SHC/SDHCI 是不同 IP，不能仅替换基址复用全部逻辑。
SDIO 超时、CRC 错和数据阶段错要分别定位。host 寄存器与参考系统吻合后，
继续比较上电时序、关联芯片控制脚、电平和时钟是否实际输出。

## DMA 验证

检查 descriptor/data 的地址可达性、对齐、长度和 Cache 方向。
验证分片边界、非对齐 buffer、短传输、多块以及错误后的再次操作。
保留合法的 bounce 或 PIO 回退。成功中断只证明请求结束，数据一致性
需要读回/哈希或已知模式测试。

ARM64 指针宽度不代表 DMA 引擎地址宽度。K7 PL330 和当时32位ADMA2路径
要求可达内存；物理4GiB从0x40000000起延伸到4GiB地址以上，不能把所有堆
都当低4GiB。CPU虚拟指针、总线地址和buffer所有权分别核对。
RX invalidate 不应破坏同cache line中仍属于CPU的脏数据；优先按底层cache
API契约分配/对齐或bounce，不能靠把整个系统cache关掉掩盖错误。

错误恢复前先证明DMA不再访问buffer，再通知完成或释放。它是硬件生命周期
条件，不是“回调已返回”就成立。吞吐测试另记请求大小、是否走bounce/PIO、
读写方向和校验，避免把协商HS400/SDR104当作实际数据面性能。

## 生命周期

初始化、暂停/停止、重启及错误恢复不能只依赖“第一次启动成功”。
重置 FIFO、清中断、撤销 DMA 和释放 buffer 的顺序要可推导；
移交所有权后不得让旧线程继续访问，失败处理必须能再次调用。

学习上游时保留来源和许可证证据。独立实现、同 IP 重用、第三方二进制
各有不同的分发条件；不要把测试结果或源站身份当许可结论。
