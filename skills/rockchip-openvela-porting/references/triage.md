# 启动故障的下一条证据

优先找出最后一个确定执行到的位置。下面每行只定义下一步区分信号，
不是要求每次重跑全表。只读检查优先；需要改固件时保留可恢复版本。

| 可观察现象 | 下一条有区分力的证据 | 不能据此认定 |
|---|---|---|
| 串口完全没有 loader 字符 | 确认串口占用/编号/1500000等目标波特率、供电和实际启动源；与已知镜像对照 | NuttX C 代码错；两个进程抢串口时“没响应”不可信 |
| loader 有字，BL33 无字 | 镜像身份、SPL 每段hash/load/entry、ELF入口与raw开头；在最早入口加单字节标记 | 立刻重写完整UART驱动 |
| 早期 putc 有字，后面消失 | 最后标记、异常向量/ESR/ELR、栈地址；确认日志是否转到 RAMLOG | 后续一定没执行 |
| 系统似乎运行但无 `nsh>` | 最终配置 `CONFIG_UART0_SERIAL_CONSOLE`/`NO_SERIAL_CONSOLE`、NSH入口及绑定设备 | 又是MMU/时钟根因 |
| 一开中断/调度就挂 | INTID换算、触发方式、pending/EOI、generic timer频率、EL异常状态 | polling UART通过即可排除架构问题 |
| 一启用某MMIO访问就挂 | 访问宽度、MMU Device映射、pclk/PD/reset、安全域；查异常地址而非盲重试写 | 地址来自DTS就一定可以直接访问 |
| 大镜像失败、小镜像成功 | FIT元数据和载荷位置、SPL工作区、扇区对齐、各段重算hash | 存在通用503KB上限或 `-E` 总能修好 |
| RC=0但新功能无符号/无行为 | `.config`、本次编译命令、linkfile实际目标、ELF符号/map与raw哈希 | 静态库里有函数就是最终固件在运行它 |
| 改头文件后出现“随机”崩溃 | 全依赖重编对照、结构体布局与对象时间、实际构建路径 | 未确认前就判硬件不稳定 |
| 冷启动好，热重启/第二次失败 | 区分软复位/硬复位/断电，读控制器和器件状态，核对in-flight DMA/写入 | 先格式化文件系统；可读GPT与卡初始化失败是两回事 |
| AMP健康RPC通过，业务大分配崩溃 | 双OS保留区、OP-TEE、实际页表、cache属性、共享区初始化代次 | health成功证明所有内存和外设所有权正确 |

## 确认实际编入与运行的是同一份

在 Linux 的 repo 工作区检查用户此次涉及的 linkfile，例如：

```sh
readlink -f vendor/rockchip/chips
readlink -f vendor/rockchip/boards
readlink -f packages/demos/contest2026_062_nyabula_core
```

第三项只适用于有 Core 的配置；不存在不是最小 NSH 失败。开发用多个隔离树时，
linkfile 仍可能指向另一树，9月20日曾实际发生“改了、编了，却没进镜像”。
用目标符号、独特版本标记、最终文件hash共同定位，不以镜像文件名判版本。

## 构建失败与依赖准备

9月20日产品 CI 的真实缺口可迁移为三项检查：

- CMake 要求 Eye 字体：先运行**该分支**字体准备入口，检查生成文件确实进入本次树。
- `agent_msg_t` 缺成员/函数：检查 framework revision、补丁应用记录和实际头文件，
  不在调用方临时重定义结构体掩盖不匹配。
- 协议宿主测试引入 `nuttx/config.h`：检查测试挑选的源文件及构建边界，
  不通过空造头文件宣称产品已构建。

这几条是特定远端head的已观察错误，不意味着其他版本永远有同样缺陷。
同样，不为避免错误擅自移除 `-Werror`、关闭模块或放宽通过条件。
