# Skill 交付与验收

本包是参赛候选，结构校验通过不等于组委会已验收。
Skill 支撑“AI 开发应用/可复用流程”的证据；作品代码、介绍文档、
演示视频及真实 AI 日志仍是独立交付项。

## 验收场景

对每行给出的输入，检查实际产出是否满足判断标准。下列是人工评估用例，
不是已经执行过的独立模型测试结果。

| 输入情境 | 应有结果 | 不应出现 |
|---|---|---|
| 新 RK35xx 板，只有 DTS 和原理图 | 列出需要核对的型号/入口/IRQ/工具链；计划最小构建和 polling UART | 直接套 K7 地址、GIC版本或刷盘命令 |
| 462 KB 能启动，503 KB 报 No matching DT | 核对 FIT header/外置数据/段落点/loader工作区，设计单变量比较 | 宣称所有镜像超过503KB都失败 |
| CMD5 超时而 host 静态寄存器匹配 | 补上电窗口、combo控制脚和CLKENA对照 | 宣称已经彻底排除软件或指定唯一必要引脚 |
| 只有编译成功，没有板子 | 交付编译证据及待板测项 | 标为实测确认 |
| 新机器拿到 Skill ZIP，无内部日志 | 使用 runbook、公有源码和所附案例摘录；明确历史原始日志缺失 | 要求访问作者私有路径才能继续 |
| 已运行 N-Boot，用户只要求检查镜像 | 检查构建/格式/哈希与只读状态 | 把旧 k7flash 固定槽位写盘当默认更新 |
| 查询旧方案为什么失败 | 引用 E1→E2 或 E3 中假设变化和验证边界 | 删除历史、把联合修复说成唯一根因 |
| 第一次为新板接 BSP，不知道文件层级 | 按source-map定位custom/内建接入、板级/芯片级和最终linkfile | 一律要求复制K7全目录或改公共arch |
| product本地能跑，CI缺字体/Agent字段 | 分开检查生成资源、依赖补丁、真实源码树 | 关闭模块或补同名假结构体让CI过 |
| 最小NSH有nbootctl但没有MMC节点 | 按配置边界判断，使用启动器加载证据 | 判定eMMC坏了或强制写盘 |
| 日志混有错误格式日期及代码内置信文本 | 报告错误日期，代码内容不当元数据 | 静默漏条并宣称全部记录合格 |

## 本包的可执行检查

在 Skill 目录：
```sh
python -B scripts/test_validate_evidence_log.py
python -B scripts/validate_evidence_log.py <实验记录.md> --strict --json
```

另可用环境提供的 skill-creator quick_validate 检查 frontmatter。
它不是本包运行依赖。检查所有相对引用在包内存在、压缩包中没有
__pycache__、凭据、私有地址或测试产物。

结构脚本只检测日期、字段、重复字段和置信标签，不判断结果是否真实、
是否符合物理规律或是否满足赛事规范。strict 失败不授权修改原始会话。

## 评分证据的呈现

评委应能很快找到：
- 改码入口与构建/产物核对：source-map.md、k7-runbook.md。
- 失败→对照→修复→边界的具体例子：kickpi-k7-case.md E1–E7；triage.md给出下一条观测。
- 可迁移方法与板型特定数值的区别：SKILL.md 和 driver-bringup.md。
- 可复用工具及其测试：scripts/。
- 尚缺证据：历史依赖锁定清单、部分内部原始日志、独立模型前向演练。

将缺项标为待补，不用“全部支持/可一键任意移植”等无法证明的表述。
