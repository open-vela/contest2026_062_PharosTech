# 实测策略与反例集

## 为什么不只改提示词

MiniCPM5-1B面对1070-token主人工具表或4/9工具表加persona时，经常描述“需要调用”而不调用。few-shot分类16/16格式正确、意图约5/16，不能用于真实执行。单工具强制补参成功更多，但无参工具、枚举外取值和相对音量仍有失败。

项目最后采用规则定意图、模型补规则无法取得的参数、同一Agent审批执行链。工具结果再次交给模型润色曾把14:05改14:00、一个五分钟计时器变多个，因此事实答复改由规则渲染。

## 已测成功

9月20日板上agent.chat实际执行时间读取、happy表情、五分钟计时器、音量30与相对减15、记忆、07:30闹钟和待办，见 `sideEffectApplied:true`。审批通过是该实验明确授权的测试动作，不应写入Skill为“所有审批自动allow”。当时设备未对时，正确执行读取不意味着现实时间准确。

## 新接入时必须重测的对照

| 输入类别 | 应检查 |
|---|---|
| 明确请求“定五分钟计时器” | 300000ms、正确主体、一次执行、审批状态 |
| “你觉得计时器这个发明怎么样” | 保持聊天、不创建任务 |
| 否定/取消/引用别人的指令 | 不误触发新动作；取消只作用到授权请求 |
| “小声一点” | 读取当前值、按定义步长和范围调节 |
| “明早七点半” | 当前时间/时区/日期含义，不擅自忽略“明早” |
| 外部客户端调用主人工具名 | scope仍拒绝，名称不授予权限 |
| 断线重试同requestId | 不重复写记忆/建闹钟；查询已执行状态 |

上表是新实现的验收要求，不声称所有否定/时间边界已在旧规则板测。

## 保持停止条件

如果规则/模型仍不能可靠区分某类意图，缩小该动作入口或返回澄清，不升级成更多自治行为。语音唤醒、ASR/TTS是另一条输入输出链，文本动作跑通不能冒称语音助手完成。
